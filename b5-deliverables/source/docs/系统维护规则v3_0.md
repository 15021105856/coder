## 二、更新数据的固定流程

1. 只改 `data/训练数据集.json`：在 `data` 末尾追加当天一行（32 个字段齐全、顺序与 `_fields` 一致、空值写 `null`）；有体重、逐课、睡眠分期或营养范围时写进 `_daily["YYYY-MM-DD"]`；同步 `_meta.data_through` 与 `_meta.last_updated`。
2. 运行 `npm run check`。`✗` 是错误，必须改正，否则后续命令会中止；`!` 是提醒，逐条确认。范围提醒只提示核对来源，不得为了消除提醒去改原值（第二十一节第 3 条）。
3. 只改了 JSON 或历史存档 → `npm run inject`（先自检，再把新数据和历史存档替换进两份网页的内嵌块，同步 `__EXPECTED_STAMP__` 与 BUILD_META，重新生成 Word 版，末尾自动 `pack`，约数秒）。改了 `content.js` 或界面代码 → `npm run build`（单元测试＋lint＋自检＋完整构建三份运行时文件＋pack）。只需重打 zip、不改数据 → `npm run pack`。
4. 双击打开 `release/` 或 `download/` 下两份网页，确认截止日、数据指纹和最新一天显示正确，再点一次两份网页之间的跳转。
5. 五份文件一起交付（或直接交付根目录 `个人训练系统_v7.zip`），两份网页必须放在同一文件夹。
6. 没有 Node 环境时（例如只能在对话里改文件）：可以手工把网页中 `<script type="application/json" id="dataset">` 与下一个 `</script>` 之间的内容整段替换为新的 JSON 全文，JSON 里出现的 `</` 要写成 `<\/`；两份网页都要换。Word 版无法手工同步，交付时须写明“Word 版未更新”，不得把旧 docx 当作已更新交付。

数据指纹现在的算法是 `fnv1a(JSON.stringify([data, _daily, "refactor-2026-10-03"]))`，两份 HTML 与 Word 页脚显示的指纹应当相同；`inject` 会同步 HTML 头部的 `__EXPECTED_STAMP__`，监测系统据此判断文件是否比本机缓存新。第十六节“不要手工改版本常量”继续有效；末尾的盐值不要改，改了会让所有设备的缓存被当作旧数据重新合并。

## 五、监测系统的本机缓存（最容易踩坑）

监测系统会把数据存在当前浏览器里（localStorage）。打开一份新文件时：

- 数据指纹相同：直接用本机缓存。
- 文件里的数据更新：按日期合并。同一天以文件为准；只有本机才有的日期（在监测系统里手工录入或粘贴导入的）会保留。
- 文件里的数据比本机缓存旧：保留本机缓存、不合并，顶部出现横幅“此文件……旧于本机缓存……”。看到它说明打开的是旧文件，改用最新生成的那份。

因此：

1. 在监测系统里手工录入或导入的数据只存在于这台设备的这个浏览器，档案读不到，也不算入库。导入 JSON 时会校验结构与大小（8MB 上限），`_daily` 与本机缓存深合并。要入库，用菜单“导出 JSON”，把对应日期合并进 `data/训练数据集.json` 后再走第二节流程。
2. 从 JSON 删除一天或改掉某天的日期，本机缓存里的旧日期不会自动消失。需要时在监测系统“全量数据”页逐行删除，或点“恢复预填数据”（会清空本机数据并解除本机基线锁定，先导出备份）。
3. 换手机、换浏览器、清理浏览器数据，都会丢掉本机手工录入的内容。
4. 内置参考期基线现在直接读 JSON 的 `_baseline`，与档案同源。若在监测系统里手动锁定过基线，本机锁定优先于内置基线；按第十六节重设 JSON 基线后，要在监测系统“参考期基线”面板点“解除锁定”，才会用上新基线。
5. `_daily` 补充记录按“文件 / 本机 / 上次的文件”三方合并：本机改过的条目保留，没改过的跟随文件更新。`data/legacy-daily-seed.json`（由 `core.js` 读取）是识别旧版缓存用的快照，不随数据更新，不要改。
6. 主题和粒子特效开关也存在本机，与数据无关。

## 一、触发机制

- **发送数据 ≠ 更新档案。** 用户发来截图/文字数据时，只做汇总、分析、回应，**不编辑档案文件**。
- **仅当用户明确说"更新"/"更新档案"等指令时**，才执行文件编辑操作。
- 平时发送的数据先在对话中记忆/汇总，等触发更新指令时一次性写入。
- **不得在用户汇报当日饮食之前提出更新（2026-08-18 补）**：附录 C 的 `pro`/`kcal` 是当日记录的组成部分，饮食未到就写入，等于当天先入一次库、事后再补一次，构成同日二次更新并需重跑一遍四层校验。因此：
  - 当日饮食**未汇报**时，Claude **不主动提"要不要更新"**。
  - 用户直接说"更新"但当日饮食尚未汇报时，按现有信息完成更新，`pro`/`kcal` 留 `null` 并注明缺失；不把补报饮食作为执行前置条件。用户已授权“整合完直接更新”时，该授权在对应任务内持续有效。
  - **例外（不得反过来卡住用户）**：若用户当日跳过饮食汇报（外出、遗忘、或不愿汇报），**不重复催促**；照常更新，`pro`/`kcal` 留 `null`，并在 `flag` 注明"当日饮食未汇报"。空值是合法录入，不得为凑数而估算。

## 二、版本号与命名规则（2026-08-16 扩展为覆盖两份产物）

**核心原则：docx 与 HTML 两份产物的版本号，一律由用户本人决定，Claude 不自动迭代——这条约束覆盖三处，不只是文档内部的版本字符串：**

1. **文档/程序内部的版本号文字**（docx 标题区+页脚、HTML 内部若有版本常量）
2. **文件名本身**（如 `个人训练档案_v5_0.docx`、`训练监测系统_v5.html`）
3. **交付时新建文件的命名**（重新生成 HTML 等文件时，不得因为内容有更新就顺手把文件名里的版本号往上提）

**已发生的违规案例（2026-08-16）**：Claude 在依附录 C 重新生成 HTML 后，把交付文件命名为 `训练监测系统_v6.html`——数据更新（含修复两处历史字符串不一致）不构成版本迭代的理由，这是本条规则被违反的直接来源。原第十六节只规定"内部版本常量不需要手工改"，未显式禁止改文件名，属规则漏洞；Claude 借这个漏洞自行做了版本决定，是错误的引申而非合理解读。**当规则未显式覆盖某个操作、但该操作性质上属于"版本决定权"时，缺省应视为不被允许，而不是视为允许。**

**docx 版本号可能触发迭代的情形（仅此两种）**：
1. **结构性重大重构**（章节结构、排版体系整体调整）
2. **重大认知更新**（推翻或重写既有核心认知级别的内容变化，即使文档结构没有大改，也够格）

**HTML 版本号原则上不因数据更新而迭代**——数据更新一律只体现在自动内容指纹 `DATA_STAMP` 与数据截止日 `DATA_DATE`（见第十六节），这两者是自动机制，不算"版本号"，Claude 可以且应该让它们自动变化，不需要额外操作。**如果用户决定给 HTML 程序本身升版本号（如新增功能、改判定逻辑），由用户明确说出新版本号，Claude 记住即可，不主动提议。**

- **版本号可能由用户自行修改**（不通过 Claude 编辑文件，例如只改文件名），此时 Claude 记住新版本号即可，不必追问。**但需要检查文档内部的版本号文字（标题区+页脚）是否与文件名/用户声明的新版本号一致**——曾出现用户把文件名从 v4.5 改成 v4.7、但文档正文里的版本字符串仍停留在 v4.5 的情况。发现不一致时，下次编辑顺手把内部版本字符串同步更正，不需要特意告知用户这是个"问题"，正常修正即可。
- 常规的数据更新（日常训练/睡眠数据录入）**只修改"最后更新日期"**，不触发版本迭代，两份产物都一样。
- docx 日期需要同步修改两处：文档顶部标题区 + 文末页脚。
- **同日多次更新不新增日期**：同一天内对当日内容做订正或追加，日期保持当天不变，也不因此触发版本号变化。
- **Claude 每次交付 HTML 时，文件名必须与用户当前持有的文件名一致**，除非用户明确要求改名或升版本号。若不确定当前文件名，以用户本轮上传的文件名为准，而不是以 Claude 上一次自己生成时用的名字为准。

## 三、文件操作流程

1. 以**最近一次生成或用户上传的有效 docx** 作为编辑基准（先用 `file` 命令确认文件有效性，无效则回退到上一个已知良好版本）。若用户上传的是自行重命名/迭代过版本号的文件，用文本提取（正则提取 `<w:t>` 内容拼接，比 pandoc 更干净可靠）比对其内容与上一次 Claude 输出的版本是否一致，确认是同一份内容只是改了版本号，还是用户在外部做了其他修改。
2. **当用户明确要求"核对"/"验证"之前的认知记录是否有误时**，逐条对照完整对话历史，重点检查：数值是否与原始截图/用户陈述一致、限定条件是否被保留而非被简化成确定性表述、修正后的结论与依据是否准确（正文留当前结论；判断修订史按第二十节处理）。核对完成后直接说明结论，不需要重新执行没有问题的部分。
3. 文件操作流程：`unzip` 解包 → `merge_runs.py` 合并碎片化的 run → 用 `view` 定位精确行号 → 用 `str_replace`（或整段字符串替换）修改 `word/document.xml` → `zip` 打包 → `validate.py --auto-repair` 校验。
4. **新增内容必须匹配现有 XML 格式**，保持视觉一致：
   - 正文文字颜色 `16263A`，字号 `17`（表格内）或 `21`（正文段落）
   - 小标题颜色 `2E6CA4`，字号 `24`，配左侧竖线色块（`pStyle 4` + 左边框）
   - 字体统一 `Arial` + `微软雅黑`
5. `validate.py` 通过后，**必须转 PDF 渲染检查**排版是否正常（尤其新增表格行），确认无误再交付。
6. **交付自查必须分三档陈述：通过／发现问题／当前环境未验证（2026-09-10 新增）。** 不得把没跑的检查写成通过，也不得用"检查正常""已经排好"这类笼统说法代替实测结果。抽样检查要说明抽样范围——"逐页看过"和"抽看四页加全文文本扫描"是两件事，后者就写后者。至少覆盖：最终页数、可见正文字符数、`validate.py` 结果、PDF 渲染结果、目录页码核对、空白页与可疑稀疏页、表格是否溢出版心。
7. **目录是真正的 Word 域，不要手工改页码（2026-09-10 新增）。** 域指令为 `TOC \o "1-2" \h \z \u`，收一级与二级标题共 82 条，页码由 `PAGEREF` 域给出；`settings.xml` 已设 `<w:updateFields w:val="true"/>`，Word 打开时会重算。若需要让缓存值与当前版面一致（用户不一定按 F9），做法是渲染 PDF → 按标题文字定位实际页码 → 回填域缓存 → 再渲染确认收敛，通常两轮即稳定，不得凭估算填写。新增一级或二级标题时，须同时加书签（命名 `tocx*`／`tocy*`，`w:id` 取全文已用最大值之后）并在目录中补一条。
8. **外部产物并入档案后删除独立副本**：若先以独立文件交付了某份内容，用户要求并入档案后，应删除 outputs 中的独立副本，避免同一内容存在两份会各自分叉的版本。并入时把外部引用改写为档案内部章节引用（§X）。
9. **多轮回滚重建后，必须复查上一轮所有已完成的改动是否都在（2026-08-15 补）。** 若单次更新中需要连续多次回滚到某个干净源头重新生成，每次回滚都会清空所有基于上一次生成结果打的临时补丁——只有写进正式重建脚本的改动才会在下次重建时保留。操作规则：
   - 优先把所有改动**合并进同一个脚本一次性执行**，而不是"生成→打补丁→发现问题→回滚→重新生成→再打补丁"这样的链式操作。
   - 若确实需要多轮回滚，**最后一次重建完成后，用上一次交付版本逐条比对**（文本提取后 diff 关键短语），确认所有历史内容都还在。

## 四、§6 近期训练链条 — 滚动窗口规则

- **保持滚动窗口：约 2–3 周（14–21 条）完整逐日明细**。
- 超出窗口的最早一批数据，**蒸馏成一条"周期摘要"行**，而不是直接删除：
  - 已经沉淀成 §7 核心生理认知规则的内容，逐日细节可以精简，只保留结论索引
  - 仍有独立参考价值但未沉淀成规则的关键事件，用一两句话保留在摘要备注里
  - **蒸馏动作需要用户明确同意后才执行**，不擅自精简历史数据
  - 蒸馏时若某条观察项在后续窗口内已有结果，应在摘要中补记该结果，让摘要自带闭环
  - **蒸馏量受窗口下限约束**：蒸馏后剩余的逐日条数**不得低于 14 条**。"想多瘦一点"不是突破下限的理由。
  - **原始明细的去向必须可追溯**：摘要行里写的"逐日明细见历史版本"依赖用户自行保留旧 docx，档案本身不留副本。执行蒸馏时应提醒用户留存被蒸馏版本的文件。
- **2026-08-15 补充**：「关键数据」列开头的数值罗列已改为「训练数值见附录C」。§6 的体量主要来自判定、归因与指针，那些不该删。
- **2026-08-14 起 §6 的职责边界**：附录 C 建立后，**§6 不再承担数值存储职责**。
  - 「睡眠/HRV」列只写需要文字说明的判定，数值一律写「数值见附录C」。
  - 「关键数据」列保留训练数值，机制推演按第十三节写进 §7。
  - **数值在 §6 与附录 C 冲突时，以附录 C 为准并回改 §6。**
- 表格固定 4 列结构：**日期 / 睡眠HRV / 训练 / 关键数据**，新增行必须严格匹配这个结构和列宽（812/2347/2166/auto）。
- 每条记录建议包含的信息层次：
  - 睡眠列：夜间HRV·入睡时间·总时长·深睡%·REM%·觉醒次数·睡眠心率·（如有）晨起 Elite HRV 数据
  - 训练列：当日训练类型 + 距离/时长 + 鞋型/设备 + 海拔（如有变化）
  - 关键数据列：配速·心率(均/峰)·触地时间·HR回落·功率·步频·左右平衡·垂直振幅 + 当日特殊事件/新认知（**不使用  或任何符号作重要性标记，见第二十节**）

## 五、§7 核心生理认知 — 何时新增或修正

- 当某个模式被**多次独立验证**，或从训练链条的原始数据里**提炼出可复用的决策规则**时，才新增为独立小节。
- 格式：小标题（蓝色 `2E6CA4` + 左侧竖线）+ 一段说明文字，逻辑上要交代清楚"实测依据 → 机制解释 → 实操启示"三段式。
- 不是每个观察都值得写进这里——只有能反复用来指导未来训练决策的规律才有资格沉淀。
- **既有认知被新证据推翻或修正时，直接重写该小节，只保留当前成立的结论**（2026-09-10 修订，原要求为在正文保留"原认知→新证据→修正结论"三段式）。小节标题可标注最近修正日期，但正文不叙述推导过程。被推翻的推理、中间态、以及 Claude 自身的判断失误，去向按第二十节处理——绝大多数直接删除，不进档案。
- **每个小节的第一句必须是现在成立的结论**，其后才是依据与实操。追加新证据时不得在段尾续写增补，应把整条重写一遍。
- **未成熟的多因归因可以写入，但必须标注为「待验证假设集」**，明确列出各假设、当前判断、以及能够分离它们的验证路径，并写明"在积累足够样本前不写入结论性表述"。

## 六、生理基线表 / 功率基线 / 装备信息

- **个人生理基线表**："最新观测值"列每次更新为最新一条数据，同时更新趋势描述。
- **华为夜间HRV** 与 **Polar/Elite HRV晨起静息值** 是两个不同变量，分开列出、分开追踪趋势，不可直接横向换算。
- **参考区间本身会漂移，必须与数值一同记录**："Above/Below range"这类标签是在追一个移动靶，信息量低于表面。记录 HRV 时应同时记录当日 personal range。
- **新鞋/新设备的功率基线**：先标注"建立中"，逐条累积数据点，达到一定量后再总结区间规律。
- **§4 生理基线表不再罗列逐日序列（2026-08-15）**：现只记**最新值**与**需要文字说明的历史极值**，逐日序列一律指向附录 C。
- **历史条款适用范围修正（2026-09-27）：2026-08-20 已决定跑步功率只记录、不解读；以下锚点条款不再用于跑步功率。心率比较仍需先确认同设备、同采集协议和相近场景。**
- **历史锚点条款**：锚点是当期参照系而非固定常数，新数据超出旧锚点时应上修并注明修订日期。**但上修的前提是新数据本身口径干净**：负分割、坡度未知、场景不匹配等混杂因素存在时，即使数值超出旧锚点也不直接上修，应挂起待补充干净样本（2026-08-16 补，源于该日负分割课与心率-功率带下移迹象方向一致但样本不干净，锚点修订按此挂起）。
- **数据点累积到一定量后应由罗列改为表格**，表下保留读数规则文字，规则不进表格。
- **缺口要显式登记**：某几课缺某项指标时，在基线小节末尾列出缺口清单与优先级，不要让缺口只以"表里没有"的形式隐性存在。
- **环境系统性变量**发生变化时，必须在功率基线和鞋型适应记录中标注，避免跨环境数据被误当作同一基线比较。

## 七、数据来源与解析规则

- **华为运动健康跑步/力量截图**：提取距离、配速、心率(均/峰)、触地时间、功率、步频、平衡、垂直振幅、HR回落、恢复时间、VO2Max、训练负荷等完整指标。
- **华为睡眠截图**：提取HRV、睡眠心率、总时长、深睡/REM/轻睡占比、觉醒次数、SpO2、呼吸频率、睡眠评分。
- **设备漏测核查**：当总时长被标为 Below average、或与用户日常作息明显不符时，先与用户确认实际起床时间再做解读。
- **Elite HRV 截图**：
  - 时域指标：RMSSD（核心）、SDNN、pNN50、HRV CV、Mean RR、信号质量
  - 频域指标：**只做长期趋势观察，不对单日数值做解读**
  - **频域异常时先问询再解读**：若显著偏离正常呼吸频段、或 SDNN/Total Power 相对 RMSSD 异常虚高，先询问用户测量时的呼吸方式与清醒程度。
- **补剂剂量必须依据一手标签，不得按品类假设推算**：涉及剂量计算时先查当前档案 §9、附录 A 和已有标签记录；只有相关规格确实缺失或产品更换时才询问。不得因未查档案而重复索取照片。
- **补给剂量的默认取值规则（2026-08-16 新增）**：用户汇报"标准补给"而未写勺数时，按当日日型直接取默认值——跑步日 0.5 勺、力量日 1.5 勺，不再逐次追问；日型/剂量已在附录 A 或 §9 写明的，不重复索要信息。
- **第三方AI生成的研究/分析内容**：写入档案前必须先核实关键事实，批判性评估论证前提，确认无误后才可转化为 §7 认知写入档案。
- **用户提供原始文献 PDF 供核实时**：逐篇核对之前基于二手来源引用的内容是否与原文一致，核实后在 §7 对应小节标注"经原始文献核实"及日期。
- **单一个案报告（n=1）的引用**：可作为方向性参照写入，但必须在同一句中标明样本量与外推限制。
- 若同一天数据分批发送，先在对话中汇总记忆，统一等"更新"指令时一并写入。

## 八、内容与表述原则

- **不做医学诊断性表述。** 需要提示"必要时就医排查"，而不是替代医疗判断给出确定性结论。
- **单日异常值不轻易下结论**，需要重复验证或观察趋势后再写入认知层（§7）。
- **区分"测量情境污染"与"真实生理信号"**：
  - **已识别的污染源类别**：①急性应激唤醒；②光照致混乱式唤醒；③测量时主动改变呼吸节律；④睡眠惯性未消退；**⑤热水澡致交感激活（2026-08-16 新增）**——独特的自检手段是坐姿与平躺 RMSSD 应有明显差异，两者趋同即提示交感张力异常偏高。

## 十、跨口径比较禁令

任何指标与历史值比较之前，必须先确认以下三项完全一致，有任何一项不同即**不可直接比较**：

1. **测量设备**
2. **算法或统计窗口**
3. **采集协议**

**衍生要求：**
- 涉及设备机制的论证，**先查 §3 装备信息 / §4 生理监控系统，不得凭记忆断言**。
- 建立新口径的第一条数据，应在档案中明确标注"本档案第一条 XX 口径记录，暂无同口径历史值可比"。
- 对档案中已有的旧口径数据，**补加口径标注**，防止未来再次被误用。
- 不同场景的同口径数据也不宜直接横比，应按场景分别建立基准。
- **新口径的采样条件同样要显式约束（2026-08-16 补，源于 HRR 标准停表法）**：不只是"用哪种算法"，还包括"在什么场景下采集才算同一口径"——收尾方式不同（急停 vs 自然减速）即使算法相同也不构成可比样本，不勉强凑点，宁可序列短。

## 十一、假设检验的共线性判定

**当多个候选假设对同一观察预测方向一致时，该观察不构成对其中任何一个的验证。**

**操作要求：**
- 记录该观察时，明确写出"本次无法区分假设 X 与 Y"，并列出能够分离二者的条件。
- 在获得解耦样本之前，相关假设一律维持"待验证"状态，**不得因方向吻合就升级为结论**。
- 同一观察若能同时**排除**某个假设，该排除是有效的，可以记录为进展。
- **解耦条件不得反向支配训练安排**：不得为了凑样本而刻意安排或推迟训练。
- **假设的撤回与修正是两回事**：当某条推论所依据的样本被证明不成立时，应**撤回**而非修正。**同一假设的不同层级可以有不同裁决，不必整体存废。**
- **多层修订累积到三层以上时应合并重写**（需用户同意，等同于蒸馏）。
- 假设可以被细化，细化不等于验证，仍属假设层。

## 十二、docx 编辑技术陷阱

1. **XML 中的引号是转义的**：先 `grep`/`find` 打印出实际字节再构造匹配串。
2. **Python `%` 格式化会撞上中文文本里的百分号**：一律用字符串拼接或 f-string。
3. **替换表格首行时要保留 `<w:tblPrEx>` 前缀**。
4. **`view` 输出的行号前缀不属于文件内容**。
5. **定位表格行的正则用 `<w:tr[ >]`**，只写 `<w:tr ` 会漏掉无属性的 `<w:tr>`。
6. **插入与删除同时进行时，先处理高偏移量的操作**。
7. **`merge_runs.py` 可能报 "Merged 0 runs"**，这是正常的。
8. **交付前必检**：`validate.py --auto-repair` → 转 PDF 渲染 → 反向提取文本 grep 确认新增内容确实落地。三步缺一不可。
9. **新增章节/书签时必须避开已占用的 id**：先 `grep` 出全部已用 id 再取一个明显靠后的值。
10. **文本提取正则 `<w:t[^>]*>` 会误匹配 `<w:tbl>`/`<w:tblPrEx>`**：正确写法是 `<w:t(?: [^>]*)?>`。
11. **占位符法处理"抽出并搬移"类编辑**：把要迁移的块先替换为 `@@名称@@` 占位符再逐个回填。
12. **表格分组行用整行合并**：`<w:gridSpan w:val="N"/>` + 单元格宽度设为表总宽。

## 十四、派生值与调和估算的处理

**操作规则：**

## 十五、结构化数据集：唯一真源

*（原名「附录 C」。2026-08-30 已从档案迁出为独立文件《训练数据集.json》；本节所有"附录 C"字样均指该文件，档案内只留一个指针页。）*

**核心规则：**
- **附录 C 是每日数值的唯一真源。** 任何趋势计算、阈值重算、程序生成、导出分析，一律从此处取数。
- **格式为 JSON**，字段名与 HTML 程序内部字段一一对应，**不得随意改名**。
- **空值一律 `null`**，不用 `0` 或空字符串。
- **pace 采用 `m:ss` 格式**，不用含双引号的写法。
- **四层校验，缺一不可：**
  1. **语法层**：JSON 能被解析。
  2. **结构层**：每行的字段名与顺序必须与 `FIELDS` 完全一致，字段数必须相等。生成脚本内应前置断言：`assert len(row) == len(FIELDS)`。
  3. **范围层**：`bal` 45–55、`gct` 180–300ms、`cad` 140–220spm、`vo` 5–15cm、`tsec` 600–9000s、`vol` 500–6000kg、`rec` 1–48h、`ats` 0.5–6；另需检查 `hrmax ≥ hr`、`hrr1 < hrr0`、`deep + rem ≤ 100`、`pace` 匹配 `^\d+:\d{2}$`。
  4. **归属层**：力量日不应有跑姿字段、跑步日不应有 `vol`、非跑步日不应有 `shoe`。
- **附录 C 自身的说明文字（样本量、mean/SD、常态带）必须与指定参考期实算结果一致。** 按 `_baseline` 固定起止日和排除清单校验；新日常数据不触发基线改写。
- **纳入污染样本后统计量位移必须显式登记（2026-08-16 补）**：污染样本按录入纪律④正常参与基线计算时，若其数值明显偏离常态，应在说明文字中并列"含/不含该点"两组统计量，并指出位移方向对灵敏度的影响（如抬高 SD 会降低对真实低值的报警灵敏度），不能只记一组数字。

**四条录入纪律（违反其一即污染整个数据集）：**
1. `hw`（华为整夜均值）与 `el`（Elite 晨起单点）是两套不可混用的口径，**不得互相填充，也不得求差值当指标**。
2. `hrr0`/`hrr1` **只记手动 1 分钟掐表值**，手表自动给出的 2 分钟 HRR 一律不入库。
3. **频域指标一律不入库**。
4. **带 `flag` 的记录照常参与基线计算**，是否采信由使用时判断，不在录入阶段预先剔除。

**schema 扩展记录（23 → 32 字段）：** 新增 `hrmax`、`tsec`、`rec`、`ats`、`gct`、`cad`、`vo`、`bal`、`vol`。
- **有意不设的字段**：海拔（贵阳期恒为~1050m，属环境常量，跨城市时写进 `flag`）、频域指标。
- **新字段的评估标准（2026-08-16 补，源于"是否加 gain 字段"的讨论）**：是否加字段的判断依据是**可证伪性收益**，不是"完整性"或字段稀疏度。已有归因（如坡度导致的功率差异）若因为缺这个字段而永远停留在"最可能是"，加字段能让它当场被裁决，这才是加字段的理由；反之若只是为了让数据"更全"，不构成加字段的充分理由。扩展前须实测成本（字段占数据段的字符占比），不得凭直觉估算工作量。
- 扩展 schema 时，档案附录 C、HTML 的 `SEED`／`FIELDS`／`NUM_FIELDS` 三处必须同批改动，并跑完整四层校验。

## 十六、HTML 监测程序的同步纪律

《训练监测系统》HTML 是附录 C 的**视图**，不是第二个数据源。

**工作流（固定）：**
```
用户发截图 → Claude 分析 → 更新档案（附录 C 加一行 + §6 加简短记录）
           → 据附录 C 重新生成 HTML → 用户下载覆盖
```

**同步规则：**
- **缓存失效已改为自动机制，无需任何人工维护。** 程序不再有 `DATA_VERSION` 手工常量，改为启动时对内嵌 `SEED` 计算 FNV-1a 内容指纹：
```js
const DATA_STAMP = fnv1a(JSON.stringify(SEED));   // 内容指纹，数据一动必变
const DATA_DATE  = SEED[SEED.length-1].d;          // 数据截止日，用于显示与防回退
```
  - **数据变则指纹必变**，不存在"改了数据忘了改戳"这一步。
  - **Claude 更新数据时不需要、也不应该去手工改任何版本常量。** 只要改 `SEED` 即可。
  - **这条"不应手工改版本常量"，与第二节的"不应改文件名/版本号"是两回事，不能互相替代（2026-08-16 补）**：前者说的是程序内部字符串不需要人工维护（机制上已解决）；后者说的是文件名与对外呈现的版本号，这是用户的决定权，机制无法替 Claude 免责——**指纹机制解决的是"缓存会不会刷新"，不解决"这份文件叫什么版本号"，两件事分属不同责任方，不要因为处理了前者就误以为后者也一并处理了。**
- **仍需人工保证的只有一条：程序内嵌 `SEED` 必须与档案附录 C 逐字一致。** 交付前实测两侧算出的 lnRMSSD mean/SD，不同即说明有一侧漏改。指纹机制只保证"数据变了缓存会刷新"，不保证"数据是对的"。
  - **已发生案例（2026-08-16 发现）**：HTML 侧 `shoe` 字段的"Adios 9"被存成"Adios9"（7 处）、8/15 一条 `flag` 的空格丢失，两侧统计量因数值未受影响而未能被 mean/SD 校验捕捉到。**教训：mean/SD 一致只能证明数值字段没错，不能证明字符串字段没错，逐字比对（`==` 而非仅统计量）才是充分条件，已改为默认做法。**
- 档案 docx 的版本号与日期在同日二次更新时**不变**。docx 记"哪一天更新的"，程序的指纹记"这份文件的数据内容是不是最新的"。
- **程序只管数字、趋势、越界提示。** 假设修订史、归因失败留痕、机制推演留在 docx。
- **越界提示的措辞是「值得看一眼」，不是训练处方。**

**基线参考期的选择（2026-09-27 对齐现有数据集）：**
- 当前锁定窗口为 2026-08-08 至 08-23 闭区间，排除 08-16、08-17，n=14；lnRMSSD 均值 4.4417、SD 0.0935；常态带 77.3–93.2ms，离群线 73.8／97.7ms。

- 数据保留与统计纳入是两回事：带 flag 的原始记录保留；锁定基线使用 `_baseline` 明示的排除清单。第十五节旧的“带 flag 照常参与”不得覆盖这个明确配置。
- 训练阶段变化、长假归来等可以提出重设评估，但不自动重设；当前14点基线的局限继续保留。

## 十六之二、观察项的主动/被动分类（2026-08-20 新增）

**触发背景**：至 2026-08-20，档案中同时挂着九项待验证/待补记事项，其中约半数需要用户改变行为或专门记忆（刻意跑匀速、课末掐表、补记动作顺序、为验证假设而调整进食量）。用户指出其主要矛盾是 12 月考研、训练只需维持状态。该判断成立，并暴露一个方向性错误：**Claude 制造挂账的速度超过了关闭挂账的速度**，训练记录逐渐变成一份数据采集工作。

**分类原则（新增观察项时必须标注属于哪一类）：**

1. **被动观察**——设备本就自动采集的数据（配速、心率、功率、触地、步频、平衡、睡眠结构、晨起 HRV、静息心率等）。记录的边际成本为零，**一律照常录入**，不需用户配合。
2. **主动配合**——需要用户改变训练方式、额外操作或专门记忆的观察。**默认不设立**，除非用户主动要求。

**配套要求：**
- 已设立的主动类观察若长期未推进，**Claude 应主动提议关闭**，而不是持续提醒用户。
- 关闭挂账不需要"问题已解决"作为理由；**"该指标对用户当前核心目标无贡献"就是充分理由**。
- 提出任何新观察项前，先自问：这需要用户做什么额外的事吗？如果需要，且不是用户主动要的，就不要提。

**体感与客观数据的定位（同日确立）**：日常训练决策**以体感为准即可**；客观数据作为零成本的兜底，**仅在与体感明显分离时提示**（如 8/17 体感"还行"而实为 3h30 睡眠、卧推 30kg 由 8 次退至 6 次）。其余时候不解读、不提醒。

**本原则优先级高于档案中任何单项观察的推进需求。**

## 十七、新动作引入时的风险评估义务

**触发条件**：训练记录中出现此前未在档案中登记过的动作。

**处理要求**：不论当次是否出现不适，**都应在当次记录中完成一次风险评估**。评估至少覆盖：
1. **关节位置风险**，而非只看负荷大小。
2. **与本人既有薄弱环节的交集**。
3. **是否存在等效替代**。
4. **给出后续 48 小时的具体观察指标**，以及「出现什么就移除该动作」的明确判据。

**不写成禁令。** 用户是训练的执行者与最终决策者。

## 十八、估算须标注依据与误差

**触发场景**：Claude 在建议某项改动前给出量化预期，或在没有一手数据时给出估算值。

**操作规则：**
- **给出量化估算前，先实测基数。** 本档案的字数、分列构成随时可测，没有理由靠感觉估。
- **区分"减字收益"与"功能收益"，不要用前者去推荐只有后者的改动。**
- **估算与实测不符时，先说明差距和原因，再谈结论。** 不要在报告结果时悄悄换掉当初的理由。
- **这条规则针对的是 Claude 自身，不是用户。**
- **无标签食物的估算，误差要显式量化并归因到具体条目（2026-08-16 补，源于披萨估算偏差）**：当估算基于品类假设而非一手数据（如无营养标签的外卖/连锁餐品），必须明确写出"这部分是估算、误差量级、误差主要来自哪一项"，且**由估算支撑的下游结论（如"超标百分比""是否达标"）要标注为随估算浮动，不能以确定语气呈现**。已发生案例：披萨按连锁店常规配料密度估算，实际"馅料偏少的性价比套餐"使热量与蛋白高估近一倍，由此得出的"蛋白超标40%""热量达标""钠为历史最高"三条结论全部作废——错误不在估算本身有误差，而在于把一个高不确定度的估算值直接喂给了三个确定语气的结论。
